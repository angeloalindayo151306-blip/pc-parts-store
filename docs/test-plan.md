# Test Plan

This plan lists what is tested, how to run each check, and what the last recorded results were. It also lists what is not tested yet.

## Strategy

| Layer | Tool | What it proves |
|---|---|---|
| Integration tests | Jest + supertest (`backend/tests/`) | Auth, role protection, checkout pricing and stock, webhook authentication, and the AI fallback, through the real Express app and the real database. |
| API collection | Postman, run with Newman (`postman/`) | Every documented endpoint over HTTP, with positive and negative cases. |
| Scenario scripts | Node scripts (`backend/scripts/`) | Payment flow, webhook handling, the expiry sweep, reviews, and the OpenAPI document. |
| Manual | Browser, Maya sandbox | The real payment, redirects, offline behaviour and the screens. |

Frontend automated tests are not part of this plan. The frontend is checked by hand (see Manual checks).

## How to run

Jest (from `backend/`):

```bash
cd /workspaces/pc-parts-store/backend && npm test
```

The tests use the real Supabase database, because the checkout and stock rules depend on real rows. `tests/setup.js` sets `NODE_ENV=test` and blanks `GEMINI_API_KEY`. Under `NODE_ENV=test` the rate limiters are skipped and the expiry job does not start. The auth tests delete the `jest-%@example.com` users they create.

Postman collection (from the repo root, with the backend running):

```bash
cd /workspaces/pc-parts-store && npx -y newman@6 run postman/pc-parts-store.postman_collection.json -e postman/environment.local.json
```

`postman/environment.local.json` is a copy of `postman/environment.example.json` with `adminPassword` set to the seeded admin password. It is git-ignored and must never be committed. The collection itself is generated by `node postman/build-collection.mjs`.

Scenario scripts (from `backend/`):

```bash
cd /workspaces/pc-parts-store/backend && node --env-file=.env scripts/<file>.js
```

`webhook-test.js`, `expiry-sweep-test.js`, `pay-test.js` and `payment-smoke.js` assert `PAYMENT_PROVIDER=mock`. The server reads `.env` at startup, so set it to `mock`, let the server restart, run the script, then set it back to `maya`. `check-openapi.js` needs no `.env`.

## Postman collection

`postman/build-collection.mjs` generates the collection. It has 11 folders and 64 requests, 30 of them negative cases:

Health, Auth, Products, Reviews, Cart, Checkout and orders, Payments, Order cancellation, AI, Compatibility, Admin.

Last recorded Newman run, against the local server with `PAYMENT_PROVIDER=maya`: **64 requests, 224 assertions executed, 0 failed.** The generator counts 161 assertion statements in the collection. I have not reconciled that figure with Newman's 224.

The run confirmed, among other things, that `?sort=bogus` gives 422 and that the admin product shows `is_active`.

Newman was also run against the deployed Render API (`--env-var "baseUrl=https://pc-parts-api-kik5.onrender.com/api/v1"`): **64 requests, 224 assertions executed, 0 failed.** The Payments folder only asserts that `checkoutUrl` is an http(s) string and `provider` is a string, so it does not prove Maya by itself. The saved report showed `provider` `maya` and the host `payments-web-sandbox.maya.ph`.

Notes for running it:

- Local rate limiters are on. One run uses about 7 auth and 3 AI calls (limits: 20 and 10 per 15 minutes), so do not run it more than once or twice in a row.
- It leaves test data in the database: a `postman-...@example.com` user, a cancelled order, and a soft-deleted "Postman Test Part". The local server and Render use the same Supabase database, so a run against Render adds the same rows.
- If every request fails at once, the server is not running. The first Newman run failed this way (224 failures, all connection refused) before the server was restarted.

## Manual checks

## Known gaps

- The Jest AI tests run with the key blank, so they cover only the fallback. The live Gemini path was seen working once by hand, and the case of live Gemini returning an incompatible build has not been seen.
- Jest does not cover the 422 `BUDGET_TOO_LOW` path of the AI endpoint.
- Jest has no tests for reviews or the compatibility endpoint on their own. Those are covered by Postman and `reviews-check.js`.
- The Jest webhook tests cover authentication only. Webhook processing is covered by `webhook-test.js` with the mock provider. `MayaProvider.verifyWebhook` was changed to need only an `id`; it was checked once by a one-off command with five inputs and dummy keys, and that check is not saved as a test. The webhook is not registered with Maya (see `docs/payment-integration.md`), so a real Maya delivery has not been tested.
- The failed-card and 3-D Secure paths have not been run against Maya.
- Lighthouse has not been run yet, because the frontend is not deployed.
- The Jest tests share the one real database with the app, so they leave no isolation between test data and real data except by the names and emails they use.
